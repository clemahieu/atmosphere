# The arch module, and why the page granule is fixed

## Decision

This is the default the aarch64 port's plan chose. The human may override it, and an override revises this record.

**Granule.** Every target translates with a 4K granule, 48-bit virtual addresses and four levels of 512 entries. `PAGE_SZ_4k`, `PAGE_SZ_2m` and `PAGE_SZ_1g` in `kernel/verified/define.rs`, the 512-entry table page and the four-level walk (`va2index`, `pagetable_map_4k_page`) stay shared constants and shared code, the same on every target. What differs per architecture is the bit layout of an entry: which bits say valid, block or page, writable, user-accessible and not executable, and where the address sits. On x86_64 that is the long-mode PTE; on aarch64 it is the VMSAv8-64 stage-1 descriptor for the 4K granule with `TCR_EL1.T0SZ = 16`. The kernel's share of every table stays the top-level entries below `KERNEL_MEM_END_L4INDEX`, copied into each process table, so on aarch64 the kernel and the process share `TTBR0_EL1` and `TTBR1_EL1` walks are disabled; the spec's split of a table into kernel and user entries does not change.

**Arch module.** Code the ISA fixes lives in an arch module, one implementation per target, chosen by `cfg(target_arch)`:

```
kernel/verified/arch/mod.rs        #[cfg(target_arch = "x86_64")] mod x86_64; pub use x86_64::*;  (and aarch64)
kernel/verified/arch/x86_64.rs     items verified code names, with their specs
kernel/src/arch/x86_64/            the same target's unverified entry glue and instruction wrappers
```

Each implementation defines the same names with the same signatures and the same `ensures`. `kernel/verified/arch/aarch64.rs` declares every item; one not yet written from the Arm manual is an uninterpreted spec function or an `external_body` placeholder counted as unproven in `tools/external-body-list`. There is no trait: shared code calls `arch::item`, and a target that lacks an item, or whose item promises less, fails to build or to verify. The specs are written over the abstract structs that already exist (`PageEntry`, `PageEntryPerm`, `Flushed`, the thread record), so the proofs above the arch module do not know which ISA they run on.

**The item set**, and where each item lives today:

1. *Page-entry encoding and decoders.* Encode an abstract entry at a level into a word and decode a word at a level back. On x86_64, all in `kernel/verified/arch/x86_64.rs`: the `PAGE_ENTRY_*` bit masks and the `MEM_MASK`, `MEM_4k_MASK`, `MEM_2m_MASK` and `MEM_1g_MASK` address masks; the decoders `usize2page_entry(word, level)`, `usize2page_entry_status(word, level)` and their specs; the encoder `page_entry2usize(entry, level)`, whose `ensures` says the word decodes back to the entry with its status clear; and the lemmas over the zero word and the status bits. The abstract `PageEntry`, `PageEntryPerm` and `PageEntryStatus` stay in `kernel/verified/pagetable/entry.rs`, and shared code reaches an entry's bits only through these items. The address masks are also read by the address checks in `util/page_ptr_util_u.rs`, `capability/map.rs` and `capability/link.rs`, each of which names the masks it reads. A table's level is a ghost field of its `PageMap`, tied to its record's level; the exec callers that decode or encode read the level from the record, or pass 4 for a root and 1 for the leaf table a walk reaches. `KERNEL_MEM_END_L4INDEX` is not an entry bit: it is the kernel's share of a top-level table, the same on every target, and stays in `define.rs`. The decoders take the level, because aarch64's bit 1 means table at levels 0 to 2 and page at level 3, where x86's PS bit means a large page; x86 ignores the argument where PS is undefined. On aarch64, in `kernel/verified/arch/aarch64.rs`, a valid word is in one of two formats and the decoders choose by the level and bit 1. A table descriptor, at levels 4 to 2, holds write and user in the hierarchical bits `APTable` and execute-disable in `UXNTable` and `PXNTable`, which bind every leaf below it as an x86 table entry's bits do, so `TCR_EL1.HPD0` stays clear. A block or page descriptor holds them in `AP[2:1]`, `UXN` and `PXN`. Execute permission is two bits there, one per exception level, and the user bits do not reach it: `AP[1]` and `APTable[0]` govern EL0's reads and writes only, so a leaf with `AP[1]`, `UXN` and `PXN` all clear is executable at EL0 as well as at EL1 (Arm ARM DDI 0487 M.d, D8.4.1.2.3 and Table D8-65; Table D8-64 for `APTable`). The abstract entry's user bit means what x86_64's U/S means, no access of any kind from user mode, and the kernel's pages sit in the table the process runs on, so the encoder writes the user bit into the execute-never bits as well. An entry that is not user has `UXN` set in a leaf and `UXNTable` set in a table descriptor, whatever its execute-disable, and its execute-disable is the EL1 bit: `PXN`, or `PXNTable`. A user leaf's execute-disable is the EL0 bit, `UXN`, and the leaf always has `PXN` set: the kernel executes no page of a process, which the architecture grants by itself only where EL0 may write the page. A user table descriptor's execute-disable is `UXNTable` and `PXNTable` together, because it binds both levels below it, as NX in an x86 table entry does. The decoders read execute-disable from `PXNTable` in a table descriptor and, in a leaf, from `UXN` where `AP[1]` is set and from `PXN` where it is clear. The round trip cannot say what the hardware does with the word, so the encoder's `ensures` says it beside the round trip, through `usize2el0_execute_never` and `usize2el1_execute_never`, which read a word as the walker does: execution at EL0 is removed exactly when the entry is execute-disable or not user, and at EL1 exactly when it is execute-disable or a user leaf. The bits that grant when clear (bit 1 for a block, `AP[2]`, `APTable`) are read against the valid bit: a valid word reads them inverted, the zero word is the empty entry, and an invalid word, which the walker ignores, still decodes to the entry the encoder was given. A valid writable leaf is the exception: the encoder marks it with the dirty-bit modifier, `DESC_DBM` (bit 51), and sets `AP[2]`, and the decoders read a leaf so marked as writable whatever its `AP[2]`, which is then its dirty state. The encoder also writes a valid leaf's memory attributes, `DESC_LEAF_ATTRS`, which the decoders ignore: attribute index 0, which `MAIR_EL1` must make Normal write-back memory, Inner Shareable, and not global.

   The item also places the two bits the walker sets, accessed and dirty, says what a word is with them clear (`spec_without_status`, and the exec `without_status` proven equal to it), and reports two facts: whether the target maintains the accessed bit and whether it maintains the dirty bit. On x86_64 the bits are `PAGE_ENTRY_ACCESSED_MASK` and `PAGE_ENTRY_DIRTY_MASK` (bits 5 and 6) and the facts are `maintains_accessed` and `maintains_dirty`, both true always. On aarch64 the accessed bit is the access flag, `DESC_AF` (bit 10), and `maintains_accessed` is true always: the walker sets the flag where `TCR_EL1.HA` is set, and where `ID_AA64MMFR1_EL1.HAFDBS` (FEAT_HAFDBS) says it cannot, a leaf whose flag is clear faults on its first access and the kernel's access-flag fault sets it. The dirty state there is not a bit the walker sets: a leaf marked with the modifier is clean while `AP[2]` is set and dirty once it is clear, so the decoder reads dirty as the modifier set with `AP[2]` clear, the encoder writes a writable leaf clean, and aarch64's `without_status` clears the access flag and sets `AP[2]` where the modifier is set. `maintains_dirty` is true always, for the reason `maintains_accessed` is: the walker clears `AP[2]` on the first write through a clean leaf where `TCR_EL1.HD` is set, and where FEAT_HAFDBS is absent the architecture leaves the dirty state to software, the write takes a permission fault on `AP[2]` and the kernel's handler clears `AP[2]` in a leaf marked with the modifier. A table descriptor is never marked, and the walker ignores both bits there. On RISC-V, Svadu says both and its absence says neither. The processor sets these bits on any core at any time, also while a core holds the kernel, so the one clear every target shares (`page_map_take_status` in `pagetable/pagemap_util_t.rs`, a glue leaf) is a compare-exchange: it replaces the word it read with the arch module's `without_status` of it, and reads again when the walker changed the word in between. What the clear writes is therefore a per-target function, proven in the arch module, which may set a bit as well as clear one, and the atomic step is written once. For the same reason the bits are not part of `PageEntry`: the abstract `PageEntryStatus` holds them, the decoder reads them from a word apart from the entry, and the encoder writes them clear, so a map leaves them clear. Two words that differ only in them decode to the same entry (`lemma_status_outside_entry` in the arch module), and a table whose words differ only there is well formed with the same view (`lemma_status_outside_view` in `pagetable/pagemap.rs`), so every proof over a table's view holds whatever values they take.
2. *Trap frame and user-return checks.* The register frame a thread record holds, the values a return to user writes (code and stack selectors on x86, `SPSR_EL1` for EL0 on aarch64) and the check that a user-supplied program counter is a user address. On x86_64: `Registers`, the all-zero frame (`zero_registers`, `zero_frame`), the selectors `USER_CS` and `USER_SS`, the flag masks `USER_FLAGS` and `FORCED_FLAGS` that `user_frame` and `user_frame_of` apply to a written frame, the `Registers` accessor `pc` for the program counter the thread returns to (rip, with its spec `spec_pc`), and `user_rip` with its exec check `is_user_rip` over the bound `USER_RIP_END`, all in `kernel/verified/arch/x86_64.rs`. `capability/thread.rs` reads them, and names no field of `Registers` and not the bound itself. The thread record holds the frame, so its size differs per target, and `kernel/verified/layouts.rs` states its layout once per target; the proofs rely only on the record ending before the thread's extended register state. The user bound differs: 2^47 on x86 (canonical lower half), 2^48 under `TTBR0_EL1` with `T0SZ = 16`.
3. *Address-space switch and flush token.* Switch this core to (root table, address-space id), and flush every context on this core, returning the `Flushed` token. On x86_64: `switch_address_space(root, asid)` in `kernel/src/arch.rs`, which every switch in `kernel/src/` calls and which composes CR3 with its no-flush bit; `flush_every_context` in `kernel/verified/arch/x86_64.rs`, which toggles CR4.PGE. The `Flushed` token, the epoch model and the IPI protocol of `design/flush-without-waiting/` stay shared; the 12-bit PCID and a 16-bit ASID both hold `PCID_MAX`. The flush stays a counted `external_body` glue leaf on each target.
4. *Syscall register table.* Which register carries each position of an invocation (the operation number, the slot, arguments 1 to 5, the status word and result words 1 to 5), the instruction, and what the call preserves and clobbers. The x86_64 and aarch64 tables are under Registers in `design/syscall-abi-in-registers/`. On x86_64: the `Registers` accessors `operation_number`, `slot` and `argument(k)` with their specs, `spec_status_word` and `spec_result(k)`, and `write_outcome`, which writes an `Outcome`'s status word and result words at their positions, all in `kernel/verified/arch/x86_64.rs`; the dispatch in `capability/operation.rs` reads the frame only through them, and the syscall handler in `kernel/src/syscalls/mod.rs` writes back only through `write_outcome`. `asys` does not link `kernel/verified`, so it carries its own copy of the table, `syscall` in `asys/src/arch/<target>.rs`, selected by the same cfg; that record is the one source both follow, for each target.
5. *Exception and interrupt entry glue.* The vector table, the stubs that save the trap frame and enter the kernel, and the instruction wrappers the stubs and the switch use. All of it is unverified glue under `kernel/src/arch/<target>/`, and the rest of `kernel/src` builds for every target: it holds no inline assembly and names no register, instruction or descriptor table, which a test in `build-tool/src/command/build.rs` checks for x86. It reaches the target through these names. `CoreState` is the target's share of a core's `Cpu` block, a field of it: on x86_64 the GDT, the TSS, the interrupt stacks and the slot the syscall entry parks the user stack pointer in. `set_core_pointer` and `core_pointer` keep and read the pointer through which a core finds its block: the GS base on x86_64. `init_boot_core` brings up the boot core once its block is in place, and `init_core` a core started later: on x86_64 the control registers, the GDT and TSS, the IDT, the local APIC and the syscall MSRs, in that order. `init(boot)` keeps what the target needs from `BootInfo`, and `translation_root(boot)` is the value a starting core loads as its translation base, which `machine::start_core` takes: on x86_64 whether PCID is on, and the PML4 with CR3's no-flush bit. `cycles` is the cycle counter the boot checks and the lock statistics time by, the TSC on x86_64, and `stall_cycles` how many of its cycles a boot check waits for another core before reporting it. `write_protect::check` writes through a read-only leaf on the calling core and stops the machine unless the write faults. `enter_userspace` enters user code at an entry point with a stack and two entry arguments, `wait` waits for the next interrupt with interrupts open, and `spin_forever` stops the core. On x86_64 these are `kernel/src/arch/x86_64/mod.rs` and `this_core.rs`, with the vector table and handlers in `interrupt/`, the syscall entry in `syscalls/` and the descriptor tables in `gdt/`.

**One verify run per target.** `tools/verify.py` checks the verified crates for the host, x86_64, and `tools/verify.py --target aarch64` checks them again under `target_arch = "aarch64"` from the same x86_64 host. That run passes rustc's built-in `aarch64-unknown-none` triple to `rust_verify`, whose `core` and `alloc` come from rustup's prebuilt `rust-std` for the triple, and points `VERUS_ROOT` at a `vstd` and `verus_builtin` compiled for it. `tools/setup-verus.sh` builds those beside the host build, under `tools/verus/source/target-verus/aarch64-unknown-none/`: `verus_builtin` with rustc, `vstd` with `rust_verify --is-vstd --compile` and its `alloc` feature, unverified because it is the source the host build verified, and the host's proc-macro libraries linked in. The shared crates' rlibs go under `target/verus/aarch64-unknown-none/`. `atmo test` runs both and holds each to `tools/verify-allowance`. Only the cfg matters to the proofs, so the triple is the built-in one rather than the kernel's own `aarch64-unknown-aloader.json`, which would need `core` built from source for the run.

**Machine glue is not the arch module.** What the platform fixes rather than the ISA (boot and discovery, the interrupt controller, the timer, the console, secondary-core start, the IOMMU) goes to a per-machine glue crate: for the PC, today's shutdown and secondary-core start in `kernel/src/boot/`, `kernel/src/console/`, `interrupt/lapic.rs`, `ioapic.rs`, `mps.rs`, `x86_xapic.rs` and `kernel/src/iommu.rs`; for aarch64, a QEMU virt crate (GICv3, generic timer, PL011, PSCI). The crate's items and the direction of the dependency are `design/machine-glue-below-the-kernel/`.

**The loader has an arch module of its own.** `aloader` is a UEFI application on every target, and most of it is shared: the UEFI calls, the memory map, the ELF load and the four-level walk that builds the first tables. What its target fixes is `aloader/src/arch/<target>.rs`, chosen by the same cfg under the same rule of one set of names: the serial device it logs to, masking interrupts, the move to its own stack, the debugger's wait, which frames of its identity map are device memory, making its root table live, dropping a page's TLB entry, the page-table entry it writes, and the kernel's entry. The loader runs on one machine per ISA, so its one device sits beside the instructions there, not in a machine crate. A test in `aloader/src/arch/mod.rs` keeps inline assembly and the port serial out of the rest of the loader. The identity map is the one place the machine's layout reaches the tables: on the PC no frame is device memory by its entry, because the MTRRs the firmware set say what is uncached, and on QEMU virt every frame below the RAM, which starts at 1 GiB, is. The aarch64 entry is the descriptor item 1 decodes, written as the kernel's encoder writes a writable entry that is not execute-disable, with two differences the loader's position asks for. The kernel runs on these tables before it can take a fault, and the loader has written the frames it maps, so each leaf has the access flag set and `AP[2]` clear beside the modifier: the writable-dirty state, which no first access and no first write faults on. And a leaf the walk's caller asks to be uncached takes attribute index 1, which `MAIR_EL1` must make Device memory; Outer Shareable, which Device memory is whatever the field holds; and both `PXN` and `UXN` whatever its `AP[1]`, because the core may fetch speculatively from Device memory that is not execute-never at every exception level, and a read changes a device's state. Item 1's decoders read such a leaf as execute-disable, which it is. An entry is arithmetic on a word, so the host's tests build the aarch64 entry beside the x86_64 one and compile the walk a second time over it; outside the tests there is one entry per target.

On aarch64, making the root table live is also where the loader writes the system-register state item 1 relies on, which the kernel then finds in place. The firmware runs the loader with translation on over tables of its own, at EL1 under a hypervisor, which the loader asserts; its `TCR_EL1` need not be the loader's, and `TCR_EL1` and `TTBR0_EL1` cannot change in one step. So the loader turns stage 1 translation off, which leaves every address its own, as the firmware's identity map had them, and writes `TCR_EL1` (`T0SZ = 16`, the 4K granule, write-back Inner Shareable walks, `TTBR1_EL1` walks disabled, `HPD0` clear, `HA` and `HD` where `ID_AA64MMFR1_EL1.HAFDBS` offers them, and the physical size `ID_AA64MMFR0_EL1.PARange` gives, up to 48 bits), `MAIR_EL1` (attribute 0 Normal write-back, attribute 1 Device-nGnRnE) and `TTBR0_EL1` with ASID 0, invalidates the TLB, and turns translation on with `SCTLR_EL1.WXN` clear, because every leaf it writes is writable, its own code's among them. While translation is off a data access is a device access the caches do not serve, so the switch is one block of instructions that touches no memory, cleaned to memory before it runs. `TCR_EL1.AS` stays clear: the width of the ASID is the switch's, item 3. The values are arithmetic on the ID registers, so the host's tests check them by bit number, as they do the descriptor.

## Reasoning

Parameterizing an entry's bit layout is cheap: the spec reads entries through the abstract `PageEntry`, and only the decoders touch bits, so a second layout is a second set of decoders proven against the same `ensures`. Parameterizing page size or level count is not: the sizes and the four-level walk appear in the page-table invariants, the memory manager's free lists, the block orders of `design/capability-names-a-block/` and the lemmas over them, and every one would become a function of the target.

Nothing chosen needs that. The aarch64 4K granule with 48-bit VA is four levels of 512 eight-byte entries indexed by 9 bits each, blocks at level 1 (1G) and level 2 (2M), pages at level 3 (4K), with the output address in bits 47:12, 47:21 and 47:30: the x86_64 shape, down to the address masks. Level 0 maps no block on either.

Selecting by cfg rather than by trait follows from there being one implementation per target. A trait in Verus carries its specs on the trait and its proofs on each impl, threads a type parameter through every caller, and buys dispatch the kernel never does. A cfg-selected module with the same names gets the same checking from the compiler and the verifier, provided `tools/verify.py` runs once per target.

Sharing `TTBR0_EL1` with the kernel keeps the kernel/user table split the spec already has. Giving the kernel `TTBR1_EL1` would be the native aarch64 layout, but it moves the kernel's entries out of every process table and changes the invariant that a table's low top-level entries are the kernel's.

## Alternatives rejected

- **A 16K or 64K granule on aarch64.** 16K gives 2048 entries a level and 32M blocks; 64K gives 8192 entries, 512M blocks and three levels. Either makes the page sizes and level count per-target through the proofs. QEMU virt and the cores under test offer 4K.
- **A trait per item, or one `Arch` trait.** Heavier in Verus, as above, for no second implementation on any one target.
- **A portability layer over the hardware**, such as a generic MMU or interrupt abstraction. The principles forbid one beyond the arch module and the machine glue, and five items do not need it.
- **The kernel in the upper half through `TTBR1_EL1`.** Native to aarch64, but it changes the page-table spec on one target only.
- **Verifying aarch64 by passing `--cfg target_arch="aarch64"` on the host triple.** rustc keeps the host's `target_arch = "x86_64"` beside it, so both modules' cfg arms are live, and pointer width and atomics stay the host's. A real target triple sets every target cfg the way the build does.

## What this does not settle

- The IOMMU. The AMD IOMMU's device IDs, command opcodes and root-table format sit in the verified tree beside the kernel model, not in an arch item; SMMUv3 on QEMU virt is a separate model, and DART on bare Apple silicon would reopen the granule.
- The aarch64 entry glue of item 5 and the switch of item 3. They are written from the Arm Architecture Reference Manual by the leaf that adds them, with the system-register state item 1 relies on: `TCR_EL1.T0SZ = 16`, `TCR_EL1.HA` set or an access-flag fault that sets the flag, `TCR_EL1.HD` set with it or a permission fault that clears `AP[2]` in a leaf marked with the modifier, `TCR_EL1.HPD0` clear, and `MAIR_EL1` attribute 0 as Normal write-back memory. Where the faults stand in for the walker, the leaves the kernel itself runs on are written with the flag set and `AP[2]` clear, so the kernel takes neither fault on its own memory.
