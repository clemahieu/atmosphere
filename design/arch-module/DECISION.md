# The arch module, and why the page granule is the target's

## Decision

Both tested targets, x86_64 and aarch64 under QEMU virt, are built this way: `tools/verify.py` verifies each against the same specs and the gate, `tools/gate.py`, boots dom0 on each. The human may override the decision, and an override revises this record.

**Granule.** The page granule belongs to the target, and the only restriction on it is that it is a power of two. A granule is a property of a translation regime, not of memory: a table is one granule of eight-byte entries, so it fixes the entries a level (granule/8: 512 at 4K, 2048 at 16K, 8192 at 64K), each level's block size (the entries times the size one level down: 2M and 1G at 4K, 32M at 16K, 512M at 64K), and, for 48 bits of virtual address, the level count and the top level's width (four levels of 9 bits at 4K; three levels of 11 bits under a top level of 1 bit at 16K; two levels of 13 bits under a top level of 6 bits at 64K). So the page size, the entries a level, the level count, the top level's width and the block sizes are the target's, and the proofs may rely on the page size only as a power of two and on what the target's translation format fixes. x86_64 has one base page size, 4K; aarch64 offers 4K, 16K and 64K where `ID_AA64MMFR0_EL1`'s `TGran4`, `TGran16` and `TGran64` say so.

What a granule does not fix stays separate from it. An IOMMU's tables are a translation regime of their own, with granules the IOMMU offers (an SMMUv3 lists them in `SMMU_IDR5`), which need not include the CPU's; every size is a power of two, so the smaller divides the larger, but a frame a device may reach must be a whole number of the IOMMU's pages and aligned to them. Firmware describes memory in 4K units (UEFI), so a region's ends are rounded inward to the granule. A device's register page smaller than the granule cannot be mapped alone. The block sizes a capability names (`design/capability-names-a-block/`) reach the ABI and the alignment of a user image's segments, so the granule reaches them too.

Both targets run one granule today, the first implemented: 4K pages, 48-bit virtual addresses and four levels of 512 entries, and the tree still assumes it. `PAGE_SZ` and `ENTRIES` in `kernel/verified/define.rs`, the 512-entry table page `PageMap` in `kernel/verified/pagetable/pagemap.rs`, the index split of an address (`L1_SHIFT` to `L4_SHIFT` and `INDEX_MASK`, in `kernel/verified/define.rs`) and the four-level walk (`walk` over a `SpacePath` in `kernel/verified/capability/mapping.rs`) are shared constants and shared code, and the rest of `kernel/verified` names the page size and the entry count through them rather than writing 4096 and 512 (`tools/check-page-literals.py`). The loader writes the 4K granule into `TCR_EL1` and walks four levels. What differs per architecture is the bit layout of an entry: which bits say valid, block or page, writable, user-accessible and not executable, and where the address sits. On x86_64 that is the long-mode PTE; on aarch64 it is the VMSAv8-64 stage-1 descriptor for the 4K granule with `TCR_EL1.T0SZ = 16`. The kernel's share of every table stays the top-level entries below `KERNEL_MEM_END_L4INDEX`, copied into each process table, so on aarch64 the kernel and the process share `TTBR0_EL1` and `TTBR1_EL1` walks are disabled; the spec's split of a table into kernel and user entries does not change.

**Arch module.** Code the ISA fixes lives in an arch module, one implementation per target, chosen by `cfg(target_arch)`:

```
kernel/verified/arch/mod.rs        the glue's tokens, then #[cfg(target_arch = "x86_64")] mod x86_64; pub use x86_64::*;  (and aarch64)
kernel/verified/arch/x86_64.rs     items verified code names, with their specs
kernel/src/arch/x86_64/            the same target's unverified entry glue and instruction wrappers
```

Each implementation defines the same names with the same signatures and the same `ensures`. `kernel/verified/arch/aarch64.rs` writes every item from the Arm manual, and its only `external_body` items are three glue leaves that x86_64 has as well, the flush, the IOMMU invalidate and the console write, counted in `tools/external-body-list`. There is no trait: shared code calls `arch::item`, and a target that lacks an item, or whose item promises less, fails to build or to verify. The specs are written over the abstract structs that already exist (`PageEntry`, `PageEntryPerm`, `TlbModel`, `IotlbModel`, the thread record), so the proofs above the arch module do not know which ISA they run on.

**The item set**, and where each item lives today:

1. *Page-entry encoding and decoders.* Encode an abstract entry at a level into a word and decode a word at a level back. On x86_64, all in `kernel/verified/arch/x86_64.rs`: the `PAGE_ENTRY_*` bit masks and the `MEM_MASK` address mask; the decoders `usize2page_entry(word, level)`, `usize2page_entry_status(word, level)` and their specs; the encoder `page_entry2usize(entry, level)`, whose `ensures` says the word decodes back to the entry with its status clear; and the lemmas over the zero word and the status bits. The abstract `PageEntry`, `PageEntryPerm` and `PageEntryStatus` stay in `kernel/verified/pagetable/entry.rs`, and shared code reaches an entry's bits only through these items. The address mask is also read by `mem_valid` in `util/page_ptr_util_u.rs` and by the address lemmas in `capability/map.rs` and `capability/link.rs`, each of which names it. A table's level is a ghost field of its `PageMap`, tied to its record's level; the exec callers that decode or encode read the level from the record, or pass 4 for a root and 1 for the leaf table a walk reaches. `KERNEL_MEM_END_L4INDEX` is not an entry bit: it is the kernel's share of a top-level table, the same on every target, and stays in `define.rs`. The decoders take the level, because aarch64's bit 1 means table at levels 0 to 2 and page at level 3, where x86's PS bit means a large page; x86 ignores the argument where PS is undefined. On aarch64, in `kernel/verified/arch/aarch64.rs`, a valid word is in one of two formats and the decoders choose by the level and bit 1. A table descriptor, at levels 4 to 2, holds write and user in the hierarchical bits `APTable` and execute-disable in `UXNTable` and `PXNTable`, which bind every leaf below it as an x86 table entry's bits do, so `TCR_EL1.HPD0` stays clear. A block or page descriptor holds them in `AP[2:1]`, `UXN` and `PXN`. Execute permission is two bits there, one per exception level, and the user bits do not reach it: `AP[1]` and `APTable[0]` govern EL0's reads and writes only, so a leaf with `AP[1]`, `UXN` and `PXN` all clear is executable at EL0 as well as at EL1 (Arm ARM DDI 0487 M.d, D8.4.1.2.3 and Table D8-65; Table D8-64 for `APTable`). The abstract entry's user bit means what x86_64's U/S means, no access of any kind from user mode, and the kernel's pages sit in the table the process runs on, so the encoder writes the user bit into the execute-never bits as well. An entry that is not user has `UXN` set in a leaf and `UXNTable` set in a table descriptor, whatever its execute-disable, and its execute-disable is the EL1 bit: `PXN`, or `PXNTable`. A user leaf's execute-disable is the EL0 bit, `UXN`, and the leaf always has `PXN` set: the kernel executes no page of a process, which the architecture grants by itself only where EL0 may write the page. A user table descriptor's execute-disable is `UXNTable` and `PXNTable` together, because it binds both levels below it, as NX in an x86 table entry does. The decoders read execute-disable from `PXNTable` in a table descriptor and, in a leaf, from `UXN` where `AP[1]` is set and from `PXN` where it is clear. The round trip cannot say what the hardware does with the word, so the encoder's `ensures` says it beside the round trip, through `usize2el0_execute_never` and `usize2el1_execute_never`, which read a word as the walker does: execution at EL0 is removed exactly when the entry is execute-disable or not user, and at EL1 exactly when it is execute-disable or a user leaf. The bits that grant when clear (bit 1 for a block, `AP[2]`, `APTable`) are read against the valid bit: a valid word reads them inverted, the zero word is the empty entry, and an invalid word, which the walker ignores, still decodes to the entry the encoder was given. A valid writable leaf is the exception: the encoder marks it with the dirty-bit modifier, `DESC_DBM` (bit 51), and sets `AP[2]`, and the decoders read a leaf so marked as writable whatever its `AP[2]`, which is then its dirty state. The encoder also writes a valid leaf's memory attributes, `DESC_LEAF_ATTRS`, which the decoders ignore: attribute index 0, which `MAIR_EL1` must make Normal write-back memory, Inner Shareable, and not global.

   The item also places the two bits the walker sets, accessed and dirty, says what a word is with them clear (`spec_without_status`, and the exec `without_status` proven equal to it), and reports two facts: whether the target maintains the accessed bit and whether it maintains the dirty bit. On x86_64 the bits are `PAGE_ENTRY_ACCESSED_MASK` and `PAGE_ENTRY_DIRTY_MASK` (bits 5 and 6) and the facts are `maintains_accessed` and `maintains_dirty`, both true always. On aarch64 the accessed bit is the access flag, `DESC_AF` (bit 10), and `maintains_accessed` is true always: the walker sets the flag where `TCR_EL1.HA` is set, and where `ID_AA64MMFR1_EL1.HAFDBS` (FEAT_HAFDBS) says it cannot, a leaf whose flag is clear faults on its first access and the kernel's access-flag fault sets it. The dirty state there is not a bit the walker sets: a leaf marked with the modifier is clean while `AP[2]` is set and dirty once it is clear, so the decoder reads dirty as the modifier set with `AP[2]` clear, the encoder writes a writable leaf clean, and aarch64's `without_status` clears the access flag and sets `AP[2]` where the modifier is set. `maintains_dirty` is true always, for the reason `maintains_accessed` is: the walker clears `AP[2]` on the first write through a clean leaf where `TCR_EL1.HD` is set, and where FEAT_HAFDBS is absent the architecture leaves the dirty state to software, the write takes a permission fault on `AP[2]` and the kernel's handler clears `AP[2]` in a leaf marked with the modifier. A table descriptor is never marked, and the walker ignores both bits there. On RISC-V, Svadu says both and its absence says neither. The processor sets these bits on any core at any time, also while a core holds the kernel, so the one clear every target shares (`page_map_take_status` in `pagetable/pagemap_util_t.rs`) is an exchange: it writes the arch module's `without_status` of the word the table holds and returns the word it replaced, and since the walker changes nothing in a word but these bits, that is the `without_status` of whatever the word held at the exchange. The exchange is the arch module's `exchange_table_word`, a hardware guarantee in the form of `design/who-vouches-for-an-unproven-claim/`, citing where each manual says the walker sets these bits in an atomic read-modify-write; `page_map_take`, which clears a word and returns it, is the same exchange of zero. What the clear writes is therefore a per-target function, proven in the arch module, which may set a bit as well as clear one, and the atomic step is written once per target. For the same reason the bits are not part of `PageEntry`: the abstract `PageEntryStatus` holds them, the decoder reads them from a word apart from the entry, and the encoder writes them clear, so a map leaves them clear. Two words that differ only in them decode to the same entry (`lemma_status_outside_entry` in the arch module), and a table whose words differ only there is well formed with the same view (`lemma_status_outside_view` in `pagetable/pagemap.rs`), so every proof over a table's view holds whatever values they take.
2. *Trap frame and user-return checks.* The register frame a thread record holds, the values a return to user writes (code and stack selectors on x86, `SPSR_EL1` for EL0 on aarch64) and the check that a user-supplied program counter is a user address. On x86_64: `Registers`, the all-zero frame (`zero_registers`, `zero_frame`), the selectors `USER_CS` and `USER_SS`, the flag masks `USER_FLAGS` and `FORCED_FLAGS` that `user_frame` and `user_frame_of` apply to a written frame, the `Registers` accessor `pc` for the program counter the thread returns to (rip, with its spec `spec_pc`), and `user_rip` with its exec check `is_user_rip` over the bound `USER_RIP_END`, all in `kernel/verified/arch/x86_64.rs`. `capability/thread.rs` reads them, and names no field of `Registers` and not the bound itself. The thread record holds the frame, so its size differs per target, and `kernel/verified/layouts.rs` states its layout once per target; the proofs rely only on the record ending before the thread's extended register state. The user bound differs: 2^47 on x86 (canonical lower half), 2^48 under `TTBR0_EL1` with `T0SZ = 16`.
3. *Address-space switch and flush tokens.* Switch this core to (root table, address-space id) through the core's `BaseRegister`, which records the core, the root and the id of the register's latest write, and flush every context on this core, which empties the core's sets of the kernel's `TlbModel`. Both are in `kernel/verified/arch/<target>.rs`: the flush is a cited hardware leaf, and the switch is verified code over cited leaves that read and write the control registers, `design/who-vouches-for-an-unproven-claim/`. The token types, `BaseRegister`, `TlbModel` and `IotlbModel`, are defined once, in `kernel/verified/arch/mod.rs`, with fields private to the arch module and closed spec accessors, so code above the module cannot build, change or copy one: Verus refuses the constructor outside `arch`, verified code cannot call `Tracked::assume_new`, which Verus marks external, and no token is `Copy` or `Clone`. Only the glue that does what a token attests makes or changes it. `load_translation_root(register, model, root, id)` takes the register by mutable borrow, so it cannot run without it, and adds `id` to the core's tags in the TLB model, which it also borrows; the capability kernel holds each core's register and lends it only from `CapKernel::switch_space`, which records the space the register names in the same step, so the record is the register's latest write, `design/teardown-driven-by-retype/`. `kernel/src` makes the registers once at boot, one per core for the root and tag it boots on, and the TLB model with every core's sets empty and the IOTLB model with every IOMMU's set empty, and hands them to `kernel_init`; `flush_every_context(model, core)` likewise takes the model by mutable borrow and is the only item that empties a core's sets of it, while proof code may only add entries. On x86_64: `load_translation_root` reads CR4 through `read_cr4` and writes CR3 through `write_cr3`, with the root and, where CR4.PCIDE is set, the PCID and the no-flush bit, the root alone where it is clear, so the register's tag is the PCID where the core tags its TLB and 0 where it does not; `flush_every_context` toggles CR4.PGE. On aarch64: `load_translation_root` writes `TTBR0_EL1` through `write_ttbr0` with the root in bits 47:12 and the ASID in bits 63:48, then an `ISB`; the write flushes nothing, and it changes the table and the id together because core bring-up clears `TCR_EL1.A1`, which makes that field the current ASID, and sets `TCR_EL1.AS`, which makes all 16 bits of it tag a TLB entry, on a core whose `ID_AA64MMFR0_EL1.ASIDBits` offers them. The TLB models, the epoch model and the IPI protocol of `design/flush-without-waiting/` stay shared; the 12-bit PCID and a 16-bit ASID both hold `PCID_MAX`, which an 8-bit ASID does not, so a core without the 16 bits stops at bring-up.
4. *Syscall register table.* Which register carries each position of an invocation (the operation number, the slot, arguments 1 to 5, the status word and result words 1 to 5), the instruction, and what the call preserves and clobbers. The x86_64 and aarch64 tables are under Registers in `design/syscall-abi-in-registers/`. On x86_64: the `Registers` accessors `operation_number`, `slot` and `argument(k)` with their specs, `spec_status_word` and `spec_result(k)`, and `write_outcome`, which writes an `Outcome`'s status word and result words at their positions, all in `kernel/verified/arch/x86_64.rs`; the dispatch in `capability/operation.rs` reads the frame only through them, and the syscall handler in `kernel/src/arch/x86_64/syscalls/mod.rs` writes back only through `write_outcome`. `asys` does not link `kernel/verified`, so it carries its own copy of the table, `syscall` in `asys/src/arch/<target>.rs`, selected by the same cfg; that record is the one source both follow, for each target.
5. *Exception and interrupt entry glue.* The vector table, the stubs that save the trap frame and enter the kernel, and the instruction wrappers the stubs and the switch use. All of it is unverified glue under `kernel/src/arch/<target>/`, and the rest of `kernel/src` builds for every target: it holds no inline assembly and names no register, instruction or descriptor table, which `tools/check-arch-sources.py` checks for x86 in the gate. It reaches the target through these names. `CoreState` is the target's share of a core's `Cpu` block, a field of it: on x86_64 the GDT, the TSS, the interrupt stacks and the slot the syscall entry parks the user stack pointer in. `set_core_pointer` and `core_pointer` keep and read the pointer through which a core finds its block: the GS base on x86_64. `init_boot_core` brings up the boot core once its block is in place, and `init_core` a core started later: on x86_64 the control registers, the performance counters, the GDT and TSS, the IDT, the local APIC and the syscall MSRs, in that order. Where CPUID offers AMD's extended core counters, the performance counters step has counters 0 to 3 count cycles not in halt, retired instructions, data cache fills and the fills that came from another CCX's cache, in the kernel and in user mode, and sets CR4.PCE so that every process reads them with RDPMC as it reads the TSC: a boot setting rather than a capability, since no process can change what is counted, with the same timing channel the TSC already opens. Elsewhere CR4.PCE stays clear. `translation_root(boot)` is the value a starting core loads as its translation base, which `machine::start_core` takes: on x86_64 the PML4 with CR3's no-flush bit where PCID is on. `cycles` is the cycle counter the boot checks and the lock statistics time by, the TSC on x86_64, and `stall_cycles` how many of its cycles a boot check waits for another core before reporting it. `write_protect::check` writes through a read-only leaf on the calling core and stops the machine unless the write faults. `enter_userspace` enters user code at an entry point with a stack and two entry arguments, `wait` waits for the next interrupt with interrupts open, and `spin_forever` stops the core. Every stack the kernel holds once it has left its boot stack, a core's syscall stack, the stacks `CoreState` holds (its `stacks`) and the second core's idle stack, is a `cpu::Stack` with a page of its own under it, and the boot core hands each such page to `guard` before another core starts, so that a stack that runs off its end faults instead of writing over what lies below; the kernel probes every page of a frame larger than one, so a frame cannot jump the page. On x86_64 `guard` clears the 4 KiB leaf the loader wrote for the page and drops this core's translation, and the page fault an overflow raises is taken on the exceptions' interrupt stack and reported once; `tools/check-boot-stack.py` forces one in the gate with the kernel feature `small_syscall_stack`, a syscall stack shallower than a syscall. On aarch64 `guard` clears the valid bit of the page descriptor the loader wrote, a change from valid to invalid that needs no break-before-make, and drops this core's translation (`TLBI VAAE1`); the overflow faults again under the vector's save of the frame, which goes to the emergency stack as below, and `tools/orangepi-stack-overflow.py --stack syscall` forces one on the board with the same feature. On x86_64 these are `kernel/src/arch/x86_64/mod.rs` and `this_core.rs`, with the vector table and handlers in `interrupt/`, the syscall entry in `syscalls/` and the descriptor tables in `gdt/`. On aarch64 they are `kernel/src/arch/aarch64/mod.rs`, with the vector table and its handler in `exception.rs`, the IRQ entry in `interrupt.rs` and the check in `write_protect.rs`. The kernel's entry is the shared `main`, which the loader enters at EL1 with interrupts masked, its table in `TTBR0_EL1`, the kernel's stack in `sp` and the `BootInfo` address in `x0`. `CoreState` is the core's emergency stack and the slot one vector spills a register to, the core pointer is `TPIDR_EL1`, `cycles` is the generic timer's virtual count (`CNTVCT_EL0`) and `stall_cycles` five seconds of it by `CNTFRQ_EL0`, `translation_root` is the loader's root as `TTBR0_EL1` holds it under ASID 0, `wait` unmasks IRQs and executes `WFI`, and `spin_forever` masks every interrupt and executes `WFI` for good. Core bring-up sets the translation control item 3 names, writes `CNTKCTL_EL1` so that EL0 reads the virtual count and its frequency without a trap, the cycle counter a process times itself by as x86_64's reads the TSC, while the physical count and both timers' registers trap from EL0, makes the vector table the core's, in `VBAR_EL1`, and has the machine set up the interrupt controller and the core's share of it; the boot core then arms its timer twice and stops the machine unless each interrupt arrives through the IRQ vector for EL1 as the timer's, the second arriving only if the first was ended. IRQs stay masked in the kernel outside that check and `wait`. The table has the sixteen vectors the architecture gives EL1, four kinds of exception from four sources. Taking an exception selects `SP_EL1` whatever the source, so every vector runs on the core's EL1 stack: it pushes the frame `Registers` describes there, `x0` to `x30`, `SP_EL0`, `ELR_EL1` and `SPSR_EL1`, calls one handler with the vector's index and the frame, and on the handler's return restores the frame, as the handler left it, and executes `ERET`. A stack that cannot take the frame, one that ran into its guard or a stack pointer that is not a stack's at all, faults under the vector's own stores, and aarch64 has no entry that changes stack by itself, as x86_64's interrupt stack table does for the double fault. That fault is a synchronous exception from EL1 on the same stack pointer, so its vector decides which stack takes the frame: when `ELR_EL1` lies in the vectors or the stub, the exception was taken under a frame's save or restore, the kernel stack took no frame and will not take this one, and the vector saves the frame on the core's emergency stack, which `CoreState` keeps for this, and hands the handler an index of its own. Entry leaves no general register free for the comparison, so the vector parks `x0` in `TPIDRRO_EL0`, which EL1 writes and the core makes no use of, and `x1` in the slot of `CoreState`, found through `TPIDR_EL1`; it clears `TPIDRRO_EL0` again before it saves the frame, and core bring-up clears it first, since EL0 reads it. The report of such a fault is the fault under the save: `FAR_EL1` is where the stack pointer was, the general registers are those the exception before it left, `x30` among them, and that exception's own `ELR_EL1` and `ESR_EL1` are overwritten. A fault under the save on the emergency stack itself repeats without end. The handler serves an IRQ, from the kernel or from EL0, and three kinds of exception. An IRQ comes through one vector whatever raised it, so the entry has the machine acknowledge it and name it (`machine::acknowledge_interrupt`, `design/machine-glue-below-the-kernel/`), runs the handler of the timer, the flush IPI or the IOMMU fault as x86_64's vectors do, and ends the interrupt; an acknowledgement that finds nothing pending returns at once, and an interrupt with no handler is logged and stops the core. One is the permission fault `write_protect::check` takes on purpose: the check maps a page of the kernel's image read-only, with `AP[2]` set and the dirty-bit modifier clear so the walker does not make it writable again, writes to it, and the handler recognises the write by its address and resumes past it with `ESR_EL1` and `FAR_EL1` as the write's result, which the check holds to a write's permission fault at the page's level and address. Another is a thread's call: a synchronous exception from EL0 whose `ESR_EL1` has the class of an `svc` executed in AArch64 state. The vector saved the thread's whole frame on the core's syscall stack, so the handler gives that frame to the verified dispatch x86_64's syscall entry calls, asks `capability::power_off_accepted` once the kernel's lock is released and has the machine shut down on a power-off the dispatch accepted, and otherwise writes the outcome over the frame through `write_outcome`; an `svc` whose immediate is not 0 returns unknown without reaching the dispatch. The stub's restore then returns every register the outcome did not take with the thread's own value, so the registers the table of `design/syscall-abi-in-registers/` calls clobbered carry no kernel value. The third is an abort from EL0 that the walker would have spared had `TCR_EL1.HA` and `HD` been set: an access-flag fault, of a data or an instruction access, and a write's permission fault. The handler in `access_dirty.rs` holds the kernel's lock, walks `TTBR0_EL1` to the leaf that translated `FAR_EL1`, and, when the leaf and every table above it give the access to EL0, sets the access flag, or, for a write through a leaf marked with the modifier that no table above makes read-only, clears `AP[2]` and drops the page from the core's TLB (`TLBI VAAE1`). The update is a compare-exchange, since another core's walker may set the flag meanwhile, and the thread then runs the instruction again; an abort of any other kind, or one whose leaf changed so that it no longer applies, is reported as below. The kernel's own leaves are the loader's, written with the flag set and `AP[2]` clear, so the kernel takes neither fault. The loader sets HA and HD where FEAT_HAFDBS offers them, and core bring-up keeps them, unless the command line's `access_dirty=fault`, a key the arch module's `set_option` takes before the machine's is asked, has every core clear them, so that a core with the feature runs the handler as one without it would. Power-off logs how many faults of each kind the handler served, and `tools/board.py --command-line access_dirty=fault` holds a run to both counts above zero. Every other exception is logged with `ESR_EL1`, `FAR_EL1` and the frame, whose `ELR_EL1` is the program counter, and stops the core, a fault in a process among them, as on x86_64. The report runs on the emergency stack whatever the exception, because a stack that took the frame may have no room left for the report, and its last line gives that stack's range and the frame's address. `tools/orangepi-stack-overflow.py` boots a kernel whose boot stack is below its boot's depth, or with `--stack syscall` whose syscall stack is below a call's, under KVM on the board, and holds it to one report, of a fault in the guard the loader or the kernel logged, with the frame on the emergency stack. `enter_userspace` builds the frame of a thread that has not run, the entry point in `ELR_EL1`, the stack in `SP_EL0`, the two entry arguments in `x0` and `x1`, every other general register zero and the `SPSR_EL1` item 2 names for user mode, writes it under the top of the core's syscall stack, where a vector would have saved it, and branches to the stub's restore. So the first entry to EL0 is the return every later exception takes, and it leaves `SP_EL1` at the top of the syscall stack, where the thread's next exception saves its frame.
6. *IOMMU command ring and invalidate.* What the IOMMU of the target's machine fixes about the ring the verified kernel sends it commands through: `IOMMU_COMMAND_SIZE`, `IOMMU_MMIO_ALIGN`, `command_ring_ok(ring, len)`, the rings its base register accepts, `IOMMU_INVALIDATE_COMMANDS`, and `invalidate_iommu_all`, the external_body glue that writes an invalidate of all the IOMMU's caches at the ring's tail, waits for it to finish and is the only item that empties the IOMMU's set of the `IotlbModel`, which it takes by mutable borrow. `CommandBuffers` in `kernel/verified/capability/kernel.rs` stays one spec over the abstract ring (an MMIO base, a ring of `len` commands in pages it holds, a tail inside it, a completion word), and its proofs do not know which IOMMU they drive. On x86_64 it is AMD-Vi's command buffer (AMD 48882): INVALIDATE_IOMMU_ALL and COMPLETION_WAIT, written at the tail register, the wait a spin on the completion word. On aarch64 it is an SMMUv3's command queue (Arm IHI 0070): CMD_CFGI_ALL, CMD_TLBI_NSNH_ALL and CMD_SYNC, written at `SMMU_CMDQ_PROD`, whose wrap bit the glue reads back, the wait a spin until `SMMU_CMDQ_CONS` reaches it; the completion word goes unused. The IOMMU is the machine's rather than the ISA's, as the console is, but the verified tree reaches per-target code only through this module, and each tested target's machine has one kind of IOMMU, so the ring sits here beside the console write while its driver, which sets the ring up and maps devices, is machine glue.

**One verify run per target.** `tools/verify.py` checks the verified crates for the host, x86_64, and `tools/verify.py --target aarch64` checks them again under `target_arch = "aarch64"` from the same x86_64 host. That run passes rustc's built-in `aarch64-unknown-none` triple to `rust_verify`, whose `core` and `alloc` come from rustup's prebuilt `rust-std` for the triple, and points `VERUS_ROOT` at a `vstd` and `verus_builtin` compiled for it. `tools/setup-verus.sh` builds those beside the host build, under `source/target-verus/aarch64-unknown-none/` of the Verus checkout at the project root: `verus_builtin` with rustc, `vstd` with `rust_verify --is-vstd --compile` and its `alloc` feature, unverified because it is the source the host build verified, and the host's proc-macro libraries linked in. The shared crates' rlibs go under `target/verus/aarch64-unknown-none/`. `tools/gate.py` runs both and holds each to `tools/verify-allowance`. Only the cfg matters to the proofs, so the triple is the built-in one rather than the kernel's own `aarch64-unknown-aloader.json`, which would need `core` built from source for the run.

**Machine glue is not the arch module.** What the platform fixes rather than the ISA (boot and discovery, the interrupt controller, the timer, the console, secondary-core start, the IOMMU) goes to a per-machine glue crate: `machine/pc` for the PC as QEMU q35 gives it (xAPIC, IOAPIC, COM1, VT-d, INIT-SIPI) and `machine/virt` for QEMU virt on aarch64 (GICv3, generic timer, PL011, PSCI). The crate's items and the direction of the dependency are `design/machine-glue-below-the-kernel/`.

**The loader has an arch module of its own.** `aloader` is a UEFI application on every target, and most of it is shared: the UEFI calls, the memory map, the ELF load and the four-level walk that builds the first tables. What its target fixes is `aloader/src/arch/<target>.rs`, chosen by the same cfg under the same rule of one set of names: the serial device it logs to, masking interrupts, the move to its own stack, the debugger's wait, which frames of its identity map are device memory, making its root table live, dropping a page's TLB entry, making the instruction fetch see an image it wrote, the page-table entry it writes, and the kernel's entry. The loader runs on one machine per ISA, so its one device sits beside the instructions there, not in a machine crate. A test in `aloader/src/arch/mod.rs` keeps inline assembly and the port serial out of the rest of the loader. The identity map is the one place the machine's layout reaches the tables: on the PC no frame is device memory by its entry, because the MTRRs the firmware set say what is uncached, and on QEMU virt every frame below the RAM, which starts at 1 GiB, is. The aarch64 entry is the descriptor item 1 decodes, written as the kernel's encoder writes a writable entry that is not execute-disable, with two differences the loader's position asks for. The kernel runs on these tables before it can take a fault, and the loader has written the frames it maps, so each leaf has the access flag set and `AP[2]` clear beside the modifier: the writable-dirty state, which no first access and no first write faults on. And a leaf the walk's caller asks to be uncached takes attribute index 1, which `MAIR_EL1` must make Device memory; Outer Shareable, which Device memory is whatever the field holds; and both `PXN` and `UXN` whatever its `AP[1]`, because the core may fetch speculatively from Device memory that is not execute-never at every exception level, and a read changes a device's state. Item 1's decoders read such a leaf as execute-disable, which it is. An entry is arithmetic on a word, so the host's tests build the aarch64 entry beside the x86_64 one and compile the walk a second time over it; outside the tests there is one entry per target.

On aarch64, making the root table live is also where the loader writes the system-register state item 1 relies on, which the kernel then finds in place. The firmware runs the loader with translation on over tables of its own, at EL1 under a hypervisor, which the loader asserts; its `TCR_EL1` need not be the loader's, and `TCR_EL1` and `TTBR0_EL1` cannot change in one step. So the loader turns stage 1 translation off, which leaves every address its own, as the firmware's identity map had them, and writes `TCR_EL1` (`T0SZ = 16`, the 4K granule, write-back Inner Shareable walks, `TTBR1_EL1` walks disabled, `HPD0` clear, `HA` and `HD` where `ID_AA64MMFR1_EL1.HAFDBS` offers them, and the physical size `ID_AA64MMFR0_EL1.PARange` gives, up to 48 bits), `MAIR_EL1` (attribute 0 Normal write-back, attribute 1 Device-nGnRnE) and `TTBR0_EL1` with ASID 0, invalidates the TLB, and turns translation on with `SCTLR_EL1.WXN` clear, because every leaf it writes is writable, its own code's among them. While translation is off a data access is a device access the caches do not serve, so the switch is one block of instructions that touches no memory, cleaned to memory before it runs. `TCR_EL1.AS` stays clear: the width of the ASID is the switch's, item 3. The values are arithmetic on the ID registers, so the host's tests check them by bit number, as they do the descriptor.

The loader copies the kernel's and dom0's segments into memory and relocates them there, through the data cache, and what it wrote is then executed. `synchronize_instructions(start, end)` is called over each range that will be: the kernel's image, and each executable run of dom0. The payload is data to dom0. On x86_64 it does nothing, because the processor keeps its instruction cache coherent with its writes. On aarch64 a fetch need not see a write until the lines written are cleaned from the data cache to the point where the two caches meet (`DC CVAU`), the instruction cache's copies are invalidated (`IC IVAU`), each is complete at a `DSB ISH`, and an `ISB` has run (Arm ARM DDI 0487 M.d, B2.2.5 and B2.7.4.2). `CTR_EL0` says what the core needs, and the item reads it: `IDC` takes the clean away and `DIC` the invalidation, and `DminLine` and `IminLine` give the line each loop steps by. The range is the addresses the code executes at, the identity map for the kernel and dom0's user addresses, which the loader's tables already map: an instruction cache indexed by virtual address drops the lines of the address it is given, not of every address the frame is mapped at (D7.5.9.13), and neither instruction takes a permission fault at EL1 on a user leaf (D7.5.9.1, D7.5.9.2). UEFI does the same for the image it loads, the loader's own. Under a hypervisor, and on a frame nothing executed from before, a run cannot tell the item's presence from its absence, so its test is the arithmetic: which steps a `CTR_EL0` value asks for, and which lines a range touches.

The aarch64 kernel's entry is a call of its `main` with the boot information's address in `x0`, on the kernel's stack as `SP_EL1`, whichever stack pointer the firmware left selected: an exception taken to EL1 runs on `SP_EL1`, so the kernel and its handlers are on one stack pointer and `SP_EL0` is a user thread's alone. Every interrupt has been masked since the firmware's services ended, which the entry asserts.

## Reasoning

Parameterizing an entry's bit layout is cheap: the spec reads entries through the abstract `PageEntry`, and only the decoders touch bits, so a second layout is a second set of decoders proven against the same `ensures`. Parameterizing the page size or the level count costs more: the sizes and the walk appear in the page-table invariants, the memory manager's free lists, the block orders of `design/capability-names-a-block/` and the lemmas over them, and each becomes a definition the target supplies. The cost is paid anyway, because a fixed granule makes another architecture implausible, which the Portability principle forbids: bare Apple silicon's IOMMU, DART, offers only 16K pages, and every aarch64 target forgoes the larger granules' shallower walks and larger blocks. Each proof written over a literal 4096 or 512 adds to that cost, so the sizes are named through the target's definitions rather than written out.

4K came first because it is the x86_64 shape: the aarch64 4K granule with 48-bit VA is four levels of 512 eight-byte entries indexed by 9 bits each, blocks at level 1 (1G) and level 2 (2M), pages at level 3 (4K), with the output address in bits 47:12, 47:21 and 47:30, down to the address masks, and level 0 maps no block on either. So the second target needed only the entry's bit layout.

Selecting by cfg rather than by trait follows from there being one implementation per target. A trait in Verus carries its specs on the trait and its proofs on each impl, threads a type parameter through every caller, and buys dispatch the kernel never does. A cfg-selected module with the same names gets the same checking from the compiler and the verifier, provided `tools/verify.py` runs once per target.

Sharing `TTBR0_EL1` with the kernel keeps the kernel/user table split the spec already has. Giving the kernel `TTBR1_EL1` would be the native aarch64 layout, but it moves the kernel's entries out of every process table and changes the invariant that a table's low top-level entries are the kernel's.

## Alternatives rejected

- **One 4K granule on every target.** It keeps the page size, the entries a level and the level count constants in the proofs, which is what the tree wrote first. It makes a target whose IOMMU offers no 4K (DART) implausible and forgoes 16K and 64K where the core offers them, against the Portability principle.
- **A trait per item, or one `Arch` trait.** Heavier in Verus, as above, for no second implementation on any one target.
- **A portability layer over the hardware**, such as a generic MMU or interrupt abstraction. The principles forbid one beyond the arch module and the machine glue, and six items do not need it.
- **The kernel in the upper half through `TTBR1_EL1`.** Native to aarch64, but it changes the page-table spec on one target only.
- **Telling a kernel stack overflow on aarch64 by the stack pointer's bounds.** A vector that compared `sp` with the running stack's lowest address would move to the emergency stack on the first fault and keep that fault's `ELR_EL1`. It needs the bounds of whichever stack the core is on: the loader's boot stack, whose guard the kernel is not told, and every stack entered later, each switch updating the core's block. Telling by where the exception was taken needs none of that, holds for a stack pointer that is wrong for any reason, and costs the first fault's return address, which `x30` in the frame stands in for.
- **Verifying aarch64 by passing `--cfg target_arch="aarch64"` on the host triple.** rustc keeps the host's `target_arch = "x86_64"` beside it, so both modules' cfg arms are live, and pointer width and atomics stay the host's. A real target triple sets every target cfg the way the build does.

## What this does not settle

- The IOMMU beyond its command ring. The AMD IOMMU's device IDs and root-table format sit in the verified tree beside the kernel model, not in an arch item; an SMMUv3 stream's identity and table format are a separate model, as DART's would be.
- Which granules each target is built and tested at, and how the gate holds the cost of verifying more than one: a run per granule, runs in parallel, or proofs over a symbolic granule.
