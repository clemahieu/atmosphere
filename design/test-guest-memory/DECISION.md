## Decision

`tools/run.py`, `tools/check-boot-stack.py`, `tools/measure-pinned.py` and `bench/run-bench.sh` boot a 2.5 GiB guest (`MEMORY_MIB`, 2560). The loader identity-maps the first 4 GiB, which is this guest's RAM and the 32-bit MMIO window just below 4 GiB, with 2M leaves; the kernel's image and its stack guard have 4K entries. Its page-table pool is 512 KiB, its bump allocator is 128 MiB, the kernel window inside that is 64 MiB and dom0's window is 16 MiB with a 1 MiB stack. The loader hands the kernel its memory map as ranges of base, bytes and type, at most 256 of them, and the kernel tracks the pages of the first 2 GiB: `NUM_PAGES` is 524,288, tiled by 1,024 2M regions and two 1G regions. Memory a range names past that is left unused, which in this guest is the top 512 MiB, where the firmware's allocations are. The second 1G region, 1 to 2 GiB, reaches the root as one untyped of order 18 at `0x40000000`, and the gate's boots require the kernel's line for it. The loader's stack and the kernel's boot stack are 1 MiB each. The kernel keeps four CPU slots, each with 64 KiB interrupt and syscall stacks. The benchmark starts four CPUs; the gate starts two.

## Context

The guest had been 32 GiB, then 6 GiB. Both were chosen from outside the kernel: 32 GiB was more than `NUM_PAGES` can track, and 6 GiB was what still fitted an Orange Pi after leaving the board's OS about a gigabyte. The loader meanwhile required one conventional region larger than a 2 GiB allocator, whether or not the guest used that allocator.

## Reasoning

The sizes are the bytes each pool has to hold, with slack where a check demands it.

- The memory map crosses to the kernel as typed ranges, which is the shape firmware gives it in, on x86_64 and on aarch64. OVMF lists 30 regions for the test guest once the loader has labelled its own; with their edges moved to pages and neighbours of one type merged they are 21 ranges of 24 bytes, in a list that holds 256. The list's length does not depend on how much memory there is, so the loader does not know how many pages the kernel tracks: the kernel checks the ranges at the trust boundary, takes the free pages below its own limit, and leaves the rest unused.
- The stacks are sized from what is written on them, measured by zeroing each, booting to dom0's exit and dumping it with `pmemsave`. The kernel's boot writes 48 KiB of its stack in a debug build and 16 KiB in release; the stack is 1 MiB, and `tools/check-boot-stack.py` requires 512 KiB of it unused. The overflow build's stack is 8 KiB, under that depth in either profile and over what `main` uses before the IDT exists. The loader's `load` writes 108 KiB of its stack in a debug build and 48 KiB in release, with the handoff and its own copies of the memory map on it; that stack is 1 MiB.
- Sixteen CPU slots with eight 1 MiB stacks each were 128 MiB of kernel image. Four slots with 64 KiB stacks are 2 MiB. Boot's copy of the handoff is on the boot stack, not on these.
- The test guest's RAM ends at 2.5 GiB. The local APIC, the I/O APIC and the IOMMU sit just below 4 GiB, and the loader only allocates below 4 GiB, so the identity map ends at 4 GiB. With 2M leaves that map is six tables: a PML4, a PDPT and four page directories. With 4K entries it is a page table for every 2 MiB besides, 2,054 tables and about 8 MiB. `tools/run.py`'s CPU model, Haswell-IBRS, has no 1G pages.
- A 2M stretch has a page table only where something inside it needs a protection of its own. The kernel write-protects one page of its image at a time (`kernel/src/arch/x86_64/write_protect.rs`), and its 1 MiB stack guard is less than a stretch, so the loader gives the stretches from the start of the kernel's image to the end of the guard 4K entries. The rest of the kernel window, the stack included, and all other memory stay on 2M leaves.
- The page-table pool is 128 pages, 512 KiB. The loader logs how many hold tables as it enters the kernel, the line `Page-table pool:` in `serial.log` after `tools/run.py`: 19, in the debug build and in release (`tools/check-boot-stack.py release`, `target/boot-stack-check-release/serial.log`). Those are 6 for the identity map, 3 page tables for the kernel's image and guard, 4 for the address space the loader builds for the IOMMU, and 6 for dom0: a PDPT, a page directory and two page tables for its image and stack, and a page directory and a page table for the payload. The most the loader can write is 55: 6, then 32 if every stretch of the 64 MiB kernel window had a page table, 4, and 13 for a 16 MiB dom0 window, which is a PDPT, two page directories and ten page tables. That fits the lower 64 pages, so the upper half, which the boot-stack check requires to stay unwritten, stays clear.
- The kernel window holds the image, 3.1 MiB with the CPU slots and the boot scratch, and the 1 MiB stack plus a 1 MiB guard. 64 MiB covers that. dom0's release image is under 1 MiB, so its window is 16 MiB with a 1 MiB stack. The bump allocator is 128 MiB, which is those two windows with room left over, and the guest's largest conventional region is larger than that without the 2 GiB floor.

- The capability kernel keeps about 48 bytes per tracked page (a 32-byte page entry, an 8-byte stale epoch, an 8-byte zeroing cursor), and boot zeroes that stretch. Tracking 8 GiB was about 96 MiB. Tracking 2 GiB is 6,170 pages with the root's boot objects, 24.1 MiB, and one byte per tracked page of boot scratch in the kernel's image, 512 KiB.
- A 1G block is one of the sizes the block table types, and a boot has to be able to produce one for anything to exercise it. The first 1G region cannot be it: it holds page 0, the legacy hole below 1 MiB, the firmware's low reservations around 8 MiB, the loader's windows and the kernel's image. So the kernel tracks a second region, and the guest has RAM past it for the firmware, which allocates from the top of RAM down.
- Measured on a boot of this guest (`tools/run.py`, debug build, the loader's `region.base()` lines in `serial.log`): the loader's kernel window is `0x1780000` to `0x577ffff`, dom0's window `0x5780000` to `0x677ffff` and the rest of its allocator `0x6780000` to `0x977ffff`, all below 256 MiB. One conventional range runs from `0x9780000` to `0x9bb5bfff` and holds all of 1 to 2 GiB. The firmware's lowest allocation above it is at `0x9bb5c000`, 443 MiB past 2 GiB; the loader's page-table pool (`0x9d5ef000`), its image and the firmware's ACPI and NVS ranges follow, up to `0x9fffffff`. The kernel puts the capability kernel at `0x6780000`, in the allocator's remainder. What is left folds to 5 free runs and 16 aligned blocks, all of which the root takes: one each of order 18, 17, 16 and 15 from `0x8000000` to `0x7fffffff`, and twelve of order 10 and below from the gaps under 128 MiB. The gate's boots, with and without the IOMMU, fail without the kernel's line `untyped base 0x40000000 order 18`.

## Alternatives rejected

- **Keep 6 GiB so the guest matches the Orange Pi.** The board is not the test. A guest that leaves the board's OS a gigabyte was a host constraint, and it hid the loader pools.
- **Stay at 32 GiB.** All but the first 2 GiB would be RAM the kernel does not track.
- **A 512 MiB guest with 1 GiB tracked.** It boots, but its one 1G region is never free, so no boot produces a 1G block.
- **A 2 GiB guest.** The firmware allocates from the top of RAM, which would then be inside the second 1G region.
- **Hand the kernel one entry per page.** At 16 bytes an entry that is 4 MiB for each GiB the list covers, copied by value onto the loader's stack and the kernel's, and a slot count the loader and the kernel must share at compile time.

## What this does not settle

RAM at or above 2 GiB is not tracked; a machine with more RAM needs a larger `NUM_PAGES`, and nothing in the loader changes with it. Nothing reserves 1 to 2 GiB: the loader allocates where the firmware's map leaves room, and the gate is what notices if that moves. The 1G block is an untyped; retype makes no 1G frame of it until the page table module maps one (design/capability-names-a-block/). A guest with RAM above 4 GiB needs an identity map past the 32-bit MMIO window; this machine has no such RAM. The 64 MiB kernel window is larger than the image and the stack it holds, and a later measurement can tighten it. The kernel's image is on 4K entries for the write-protect check alone; a check that split the leaf it tests would let the image share 2M leaves with the rest.
