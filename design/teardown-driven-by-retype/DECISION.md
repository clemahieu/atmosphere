# Teardown is driven by retype

## Decision

Each capability, hidden node and mapping holds a reference on its object's block. Page metadata holds at 4K a type, block order, stale epoch and zeroing cursor, with a reference count at the block's base, and at 2M and 1G a count of typed units, so a retype checks freedom in constant time. Zeroing happens before a capability names memory: at once for 4K, in 64 KiB chunks for larger, with the cursor in the metadata, so a later retype of an abandoned block resumes it.

A binding holds a reference too. What holds a reference is a list node, a capability, a mapping, a hidden node or a binding, and only revoke or teardown removes it. What holds none is a record that points back along such a node: a leaf's parent record, a thread record's process, a reply's bound caller. A back-pointer is cleared in the same step as the node that justified it, so it names a live object or nothing and keeps nothing alive. The count's job is the free check at retype, not the definition of death: a thread's binding holds its process while the process's table holds the thread's capability, so references alone would never reach zero there. Destroy through a control capability is the second way to die, and the holder of the untyped above both clears the counts by revoking its lineage before it retypes.

An object is dead when its block's references reach zero, and a process or thread also when destroy is invoked through a control capability, since a control capability holds a reference and claim needs one to survive the death. Either is one bounded step. Every operation refuses a dead target, except a claim, which is a move out of a controlled process's table, and revoke or delete of a capability naming it. A dead process's threads stop at the next kernel entry: each core checks its current thread's process on entry and on exit, one load each, and an IPI to the process's loaded cores forces that entry.

The kernel never kills on its own. A fault stops only the faulting thread, Inactive with its fault recorded, and sends the fault message if a fault endpoint is named; a stopped thread's registers are readable through its control capability. So destroy is the only way to be dead while references remain.

There is no kernel list of dead objects, and no revoke or delete drains another's teardown. A retype naming a block, by a holder of an untyped covering it, does the work: on a free block it types it; on a block with a hidden node it unlinks that node, so a pager can reclaim a live process's interior leaves and tables; on a dead object with zero references it does a bounded slice of teardown and returns `again` until the block is free; on anything still named by a capability it is refused, and that holder revokes those first.

Every block no capability names has a hidden node, node 0 of its first node page, a child of the untyped it came from: table leaves and table pages. So revoking the untyped reaches them, and a retype can name one alone. A process's address space root and table root are inside the process object, so they go only with the process, once no core depends on its space. A core stays on a space's list of cores once it has loaded the space, so the list alone would refuse such a retype for ever. A retype of a dead process's block whose space a core still depends on retires the space instead, when no core's page-table base register names the space: it raises the flush epoch, records it as the space's retire epoch and sends the listed cores the flush IPI. Each core's state records the space its base register names, which only `CapKernel::switch_space` in `kernel/verified/capability/mapping.rs` writes, in the step in which it writes the register through the arch glue `load_translation_root` and the core's `BaseRegister`, which the kernel holds and lends to nothing else, so the record is the register's latest write; and only for a space the core has loaded that is not retired, written under the PCID or ASID the space holds on that core, which the register records, so what the core caches after the write is under that space's tag. The tag stays the space's alone while the register names it: the space keeps a valid id on the core, since a load that would start a new generation of ids, which leaves none valid, runs only while the register names no space or the space it loads. A register that names no space is written under `KERNEL_TAG`, the one tag no space is handed, so nothing the core caches then is under a space's tag; and it names the root the core booted on or a root at no space's root offset. Every space's root is at the same offset of a block of the table block's size, so no retype can make the latter a space's root; the former's page is one `kernel_init` requires boot to hand to no block, and the invariant keeps it Reserved, since nothing after boot types a Reserved page, so it is in no block and is no space's root either. So the record never says no space while the register names one (`CapKernel::lemma_none_names_no_root`). That the boot root is the kernel's own is the glue's, below. A core whose register named the space after its flush could fill its TLB from the space again, so the retire refuses while one does; a core translates through no root but the one its register names, so the register is the whole of what the retire asks of a core. A listed core whose acknowledgement has reached the retire epoch no longer depends on the space, no register can name it until a later load of the space clears the retire epoch, and that load makes the core depend on it again. So the retype that frees the block reads the list, the retire epoch and each listed core's acknowledgement, and refuses while a core depends; `CapKernel::process_released` in `kernel/verified/capability/reclaim_process.rs` states it. An IO or nested space has its own root, which goes after the bindings under it are undone.

Nothing can be added behind a dismantle's cursor. What the hardware walks is detached first: every table page records its parent, the root pointer or table entry that points at it, and detach is two-way in one bounded step: clearing a parent's pointer also clears the child's record, and a child with no record skips the parent write. So a parent record names a live block or nothing. The capability table is walked by software only, through `Tables::lookup` (`kernel/verified/capability/table.rs`), which refuses a slot in a leaf whose hidden node is dead, one load of node 0 of the leaf's page. So a table leaf is not detached: it stays in its root entry, inert, until its own retype frees it, and that free clears the root entry its parent record names, the same two-way clear in one step. A root entry names a live leaf or nothing, a leaf's owner always names a root the tables hold, and a dead process's block frees only when its table root is empty, waiting for its leaves' retypes as it waits for its threads' bindings. Unlinking a hidden node, by revoke or by retype, detaches a table page and drops the reference, and for a leaf only drops the reference; the rest is dismantle, on a dead block, in slices of the retype that drives it, so a revoke stays exactly its lineage. A leaf or table page a process leaves behind is unreachable and inert, keeping its hidden node until its own untyped's holder retypes it. So is a thread whose process binding was revoked: it cannot run or be bound again, its registers stay readable through its control capability, and its block goes when its untyped's holder retypes it after the capabilities naming it are gone, `design/thread-bound-at-retype/`. A thread Running when its binding goes gets a pending stop and its core's IPI, and leaves the core at that core's next kernel entry, as a dead process's threads do. An endpoint wakes its queue with an error. A dead object nobody retypes keeps its memory, its nodes stay linked in other lineages, inert, and a thread blocked on it stays blocked until the holder drives teardown. Collecting while idle is the holder's policy, charged to the holder.

Rules: a retype or regrant requires zero remaining mappings and no stale translation on any core, `design/flush-without-waiting/`, and a thread object or loaded address space cannot be retyped while a core depends on it: a core depends on a space it has loaded until it acknowledges the flush that retired the space. The prover keeps the record the register's latest write: no verified code outside the arch module can build, change or copy a `BaseRegister`, since its fields are private to the arch module and one of them is of a type private there that is neither `Copy` nor `Clone`, so rustc refuses an `impl Copy` for it anywhere else, and the gate refuses the unsafe code that could zero one up or read one out twice; and only `switch_space` lends one to `load_translation_root`, `design/arch-module/`. The prover does not tie the core `switch_space` is given to the core it runs on: `load_translation_root` writes the running core's register, so the caller of `switch_space` owes that it passes the core it runs on, as its one caller, the boot in `kernel/src/capability.rs`, does by running on CPU 0 and passing 0. The gate keeps the glue counted: `tools/check-external-body.py` matches every `external_body`, `exec_allows_no_decreases_clause` and `assume_specification` in a crate marked verified against `tools/external-body-list` and refuses every other exemption from the proof (`assume`, `admit` or `assume_` named in code, outside every comment and literal as rustc reads them, under any name it is imported as; an axiom; `verifier::external` or any other verifier attribute whose name starts with `external`, among them the external function, trait and type specifications; any attribute under `verus::internal`; `assume_termination`; `assume_unsupported_attributes`; an `assume_new` constructor outside the body of a counted `external_body` function; `unsafe` outside that body and the body of a function an `assume_specification` in the same file names, since only unsafe code makes a value of a type whose fields it cannot name or copies one that is neither `Copy` nor `Clone` (`core::mem::zeroed`, `core::ptr::read`, `MaybeUninit::assume_init`, `transmute`), and Verus does not read an impl outside `verus!` that verified code reaches through a trait such as `Default` or `From`; any unstable feature), reads a first line opening `#!` as rustc does, and refuses any file the crate compiles that it does not read (a path attribute, an `include!`, a module named `target`), so the glue named here is all the prover takes on trust; what that glue and its callers owe, here and below, no step of the gate checks. The glue keeps what the retire assumes: each write of a core's page-table base register after the kernel runs on the core goes through `load_translation_root`, and `kernel/src`, which makes other tracked values with `Tracked::assume_new`, makes the cores' `BaseRegister`s once, at boot, for the root and tag each boots on, and makes no other; the write before it, by the loader on the first core and by the machine glue that starts each other core (`machine/pc`, `machine/virt`), stands for a `switch_space` to no space; every write naming no space, before the kernel runs or after, is of the kernel's own root, the loader's table in the page-table region its memory map hands the kernel as taken, under tag 0, `KERNEL_TAG`, so the root is a page outside every untyped and every 2M region of dom0's image, which `kernel/src` checks before `kernel_init` requires it, and maps no page a space maps; and a core runs a thread only in the space of the process it is bound to.

## Context

Marking dead is one bounded step, but clearing a process's contents takes many, and something must drive them. Two drivers were put to the human: the block's next user, or a kernel list that any revoke or delete advances. Separately, a process with a controller could never reach zero references, so there had to be a second way to die, and whether a fault with no handler should kill the whole process.

## Reasoning

Charging teardown to the party who wants the memory keeps reach exact: no process touches objects outside what it holds, and the theorem needs no housekeeping attributed to no one, `design/theorem-over-reach/`. A kernel list would make one process do another's teardown, and a process killing a large one would slow everyone's revoke until it drained. The cost, memory held by dead objects nobody retypes, is accepted; a pager that wants it back retypes.

Two reviews found what the order of operations had to be: dismantling before detaching left a zombie writable (a grant into a torn-down process, a map through a table page being cleared), bindings that the count did not hold could be freed and retyped under the kernel, and a parent record that outlived its parent could write into a block another process now owned. Two-way detach, bindings as counted nodes, and the hidden-node arm doing no more than detach and its reference are the answers, each now a stated invariant.

On kill policy: seL4, NOVA, L4Re, Genode, KeyKOS, EROS and Barrelfish stop or report the faulting thread and leave the decision to user level; Unix, Windows NT and Zircon kill the process. The kernel here decides no kill policy, so the thread stops and a supervisor destroys and claims, `design/sharing-by-derive/`. Crash dumps, graceful unwinding, migration and paging to disk were each checked as a supervisor, runtime or pager protocol over suspend, readable registers, claim, fault messages and revoke.

## Alternatives rejected

- **A kernel zombie list advanced by any revoke or delete.** See above.
- **A fault with no handler kills the whole process.** One thread's fault would end its siblings, which a process with its own recovery could avoid only by naming a fault endpoint.
- **Detaching a table leaf from its root entry at unlink, as a table page is.** The view attributes a leaf's capabilities to the process its owner names, so a detached leaf keeps an owner whose root entry no longer names it, and the process block could free and its base be retyped while those capabilities are still attributed there. Keeping the owner sound then needs a count of owned leaves, which the root entries already hold, or a sentinel owner, which grows the sentinel's reach and the theorem's statement. A refusing lookup needs neither: the entry itself says the leaf is still the process's.
- **Teardown at zero references with no driver.** Dangled: a table's node pages could be freed while nodes on them were in another lineage, and a revoked thread could keep running with nothing left to stop it.
